# 容量与并发实测（教培机构落地前的体检）

> 所有数字都是 2026-09 在真机（EVO4，微课堂 2.0.0）上实测出来的，不是估算。
> 复现命令见每节末尾。

## 0. 结论先看

| 环节                                        | 实测                                                                                                 | 判断                                             |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 服务端 + 磁盘（20 路并发取同一 1080p 视频） | 合计 **623 MB/s**，单流最低 32 MB/s                                                                  | **完全不是瓶颈**（20 路 1080p 只需要 ~8.6 MB/s） |
| 单流首字节（TTFB）                          | 本机 2–3 ms｜局域网客户端 37 ms                                                                      | 服务端响应很快                                   |
| **客户端实际下载速度（当前部署）**          | 单流 **1.3 MB/s（10.5 Mbps）**；8 路并发合计 **3.1 MB/s（26 Mbps）**                                 | **这才是「视频加载慢」的原因**                   |
| **重查询期间的流媒体**                      | 一边播视频一边跑 `banks/health?refresh=1`（69.9 s）→ 该流从 30 s 拖到 **73.4 s**，均速掉到 0.86 MB/s | **一个人点体检，全班视频一起卡**                 |

两个根因：

1. **NAS 自己走在 WiFi 上**（`ip route` 显示出口是 `wlp4s0`，`<NAS-IP>` 在无线网卡上），
   而客户端多半也在 WiFi —— 每个字节要过两次空气，实测只剩十几 Mbps。
   **同一台机器上的有线口 `enp2s0` 是 UP、1000Mb/s、link detected**，只是没接/没配 IP。
2. **SQLite 是同步 API，重查询会把 Node 的事件循环整个占住** —— 期间所有流都被饿死。

## 1. 服务端能力（不是瓶颈）

```
单流 50MB（热缓存） ： TTFB 3 ms，288 MB/s
单流 50MB（冷缓存） ： TTFB 2 ms，295 MB/s      ← 冷热几乎一样
20 路并发 × 20MB    ： 合计 623 MB/s，最慢单流 32 MB/s（257 Mbps）
```

磁盘顺序读：`/vol2`（思酷睿课程，53.8 GB 视频）**203 MB/s**；
`/vol1`（数据库卷）**74 MB/s**。
（此前文档里写的「顺序读 ~1.9 MB/s」是错的，已按实测更正 —— 那是随机小读 + 当时磁盘争用下的数字。）

复现：

```bash
# 20 路并发
sudo docker exec microclass-api sh -c "seq 1 20 | xargs -P 20 -I{} curl -sS -b /tmp/cookie \
  -o /dev/null -w '%{speed_download}\n' -r 0-20971520 'http://127.0.0.1:8091/api/v1/lessons/<id>/video'"
# 磁盘
dd if=/vol2/1000/思酷睿课程/<某个>.mp4 of=/dev/null bs=1M count=200
```

## 2. 客户端路径（真正的瓶颈）

| 场景                                      | 单流                      | 8 路并发合计            |
| ----------------------------------------- | ------------------------- | ----------------------- |
| 现在（客户端 WiFi ↔ NAS WiFi，同一个 AP） | **1.3 MB/s（10.5 Mbps）** | **3.1 MB/s（26 Mbps）** |

按视频码率换算（实测样本：1080p H.264 **3.4 Mbps** + AAC 128 kbps；小初高数学课件多为
480p 级 ~0.4–1 Mbps）：

| 线路                                           | 1080p（3.4 Mbps） | 720p（~1.2 Mbps） | 480p（~0.6 Mbps） |
| ---------------------------------------------- | ----------------- | ----------------- | ----------------- |
| 当前（26 Mbps 实测）                           | ~7 路             | ~20 路            | ~40 路            |
| NAS 接网线、客户端有线（千兆，按 600 Mbps 计） | ~170 路           | ~500 路           | ~1000 路          |
| 机构 100 Mbps 上行（校外访问）                 | ~25 路            | ~80 路            | ~160 路           |

> 也就是说：**现在的「慢」主要是网络，不是服务器**。把 NAS 插上网线，是投入产出比最高的一步。

## 3. 会影响体验的具体缺陷（按优先级）

| #   | 问题                                      | 证据                                       | 影响                                                                          |
| --- | ----------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------- |
| 1   | 视频响应头 `cache-control: no-store`      | `curl -D -` 实测                           | 浏览器与任何反代/CDN 都不能缓存 → 重复观看、拖动进度都回源                    |
| 2   | MP4 没有 faststart（`moov` 在文件末尾）   | 364MB 文件的 `moov` 距末尾仅 **817 KB**    | 播放器必须先取一次文件尾部才能起播；弱网下每次起播多一次往返                  |
| 3   | 3,768 个课时里 **1,130 个视频路径不存在** | 按 `settings.media_roots` 解析后 stat 失败 | 学生点到这些课时直接报错，看起来就是「打不开/很慢」                           |
| 4   | 重查询阻塞事件循环                        | 上面的 69.9 s / 73.4 s                     | 一人点体检/去重/重算，全员视频一起卡                                          |
| 5   | 限流是「每 IP 300 请求/分钟」             | `MC_RATE_LIMIT_MAX=300`                    | 一个机构一个出口 IP：30 个学生同时用很容易打满；拖动进度条的 Range 请求也计数 |
| 6   | 只有单一 1080p 码率，无 HLS/多档          | ffprobe 实测 3.4 Mbps                      | 教室 WiFi 挤的时候没有「降清晰度保流畅」的退路                                |
| 7   | 媒体由 Node 进程直接吐                    | `utils/range.ts`                           | 视频连接与 API 共用一个进程，API 被阻塞时视频跟着受害                         |

## 4. 建议的实施顺序

**第 0 步（零代码，收益最大）**

- 把 NAS 插上网线（`enp2s0` 已是千兆口），并让微课堂监听/路由走有线口；
- 教室 AP 尽量 5GHz、与 NAS 同交换机；能接有线就接有线。

**第 1 步（代码/数据，一次做完）**

- 视频响应改为可缓存：`cache-control: private, max-age=86400` + `etag/last-modified`
  （保持 `private`，视频仍需登录才能拿）；
- 批量 faststart 重封装（`ffmpeg -c copy -movflags +faststart`，不重编码，2,638 个文件 / 53.8 GB，
  按 200 MB/s 估算十几分钟）；
- 修 1,130 个失效路径（重新扫描媒体目录修正 `media_root/video_path`，或标记为不可用并隐藏）；
- 限流按「登录用户」计数，媒体路由单独放宽/白名单。

**第 2 步（解决「一人卡全班」）**

- 重活（体检、去重、难度重算、冲突重扫）改成后台任务 + 进度查询，不在请求路径上跑全表扫描；
- 前面加一层 nginx 负责媒体（sendfile + 缓存），Node 只管 API —— API 忙时正在播的视频不受影响；
- 长任务期间给 `bankService` 的缓存加「单飞」（同一个 key 只允许一个在算）。

**第 3 步（面向 100+ 学生 / 家校两端）**

- 转 HLS 多码率（1080p / 720p / 480p）或至少生成 720p 版本，学生端可手动切档；
- 视频放独立媒体服务或对象存储（NAS 只做存储）；
- 若开放公网，先测机构上行带宽：100 Mbps 上行约等于 25 路 1080p / 80 路 720p。

## 5. 复现命令汇总

```bash
# 出口网卡（确认 NAS 是不是在 WiFi 上）
ip route get 192.168.0.1

# 响应头（确认有没有缓存头 / range 支持）
curl -sS -b /tmp/cookie -o /dev/null -D - -r 0-1023 "http://<host>:8091/api/v1/lessons/<id>/video"

# moov 位置（判断有没有 faststart；末尾 4MB 内能找到 moov 就是没优化）
node -e '...'   # 见 build/ 下的临时脚本，或 ffprobe -v trace | grep moov

# 事件循环阻塞：一边流一边跑重查询
curl -sS -b /tmp/cookie --limit-rate 2M -o /dev/null -w '%{time_total}\n' -r 0-62914560 "…/video" &
curl -sS -b /tmp/cookie -o /dev/null -w '%{time_total}\n' "…/banks/health?refresh=1"
```
