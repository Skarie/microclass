# P0：数据层从 SQLite 迁到 PostgreSQL

> 目标：把「单文件 SQLite + 同步驱动」换成「PostgreSQL + 连接池 + 异步访问」，
> 为后续的**多实例、读写分离、异步任务、高可用**打地基。
> 本文档记录**已验证**的迁移路径、实测数据、切换 Runbook 与回滚方案。

## 1. 为什么必须换

| 现状                                           | 后果                                                                                  |
| ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| `node:sqlite` 的 `DatabaseSync` 是**同步** API | 任一慢查询阻塞整个事件循环，`/healthz` 也会超时（2026-11-26 00:06 整站无响应 5 分钟） |
| 单文件、单写者、文件级锁                       | 无法多实例写；备份/扩容都受限                                                         |
| 无连接池、无读副本                             | 体检这类全表聚合只能和在线请求抢同一块盘                                              |
| 与机械盘耦合                                   | 数据落在单盘「RAID1(1 设备)」上，无冗余                                               |

**这不是"要不要"的问题，是企业级高并发/高可用的前提**：没有独立、可并发、可复制的数据库，
后面的多副本、队列、读分离都无处落地。

## 2. 已验证结论（本次实测）

| 项目         | 结果                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| Schema 转换  | 30 张表 / 54 个索引 / 21 个外键 / 3 个触发器 全部生成并成功建库                                             |
| 数据导出     | 454,097 行 → 512 MB TSV，**150.5 s**                                                                        |
| 数据装载     | 30 张表全部装入 PG 16，**195 s**（其中 `questions` 396,505 行 / 185 s）                                     |
| 行数校验     | 30 张表 **全部一致**                                                                                        |
| 内容指纹     | 10 组「COUNT + SUM(id) + SUM(文本长度)」**完全一致**（含 questions/banks/lessons/courses/knowledge/users…） |
| 全表聚合性能 | `SELECT COUNT(*) FROM questions`：SQLite **2,370 ms** → PG **27 ms**（≈88×）                                |
| 索引点查     | 单课时 50 题：SQLite 0.7 ms / PG 3.8 ms（PG 数字含 `docker exec`+psql 启动开销，接入连接池后为亚毫秒级）    |
| 迁移环境     | 临时 PG 16 容器（`mc-pg`，端口 55432，独立数据目录），**生产未受任何影响**                                  |

> 测试机：NAS 机械盘（`/vol1`），数据同一份，PG 数据目录也在同一块盘上 —— 还没算上「换到 SSD」的收益。

## 3. Schema 映射规则（生成器已实现）

| SQLite                                        | PostgreSQL                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `INTEGER PRIMARY KEY AUTOINCREMENT`（17 处）  | `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`                                     |
| `INTEGER` / `REAL` / `TEXT` / `BLOB`          | `bigint` / `double precision` / `text` / `bytea`                                          |
| `DEFAULT (unixepoch())`（16 处）              | `DEFAULT (EXTRACT(EPOCH FROM now()))::bigint`                                             |
| `CHECK (...)`（8 处）                         | 原样保留为表级 `CONSTRAINT`                                                               |
| 部分索引 `CREATE INDEX ... WHERE ...`（7 处） | 原样保留（PG 原生支持）                                                                   |
| `UNIQUE`（3 处）                              | 延后为 `ALTER TABLE ... ADD CONSTRAINT`                                                   |
| 外键（21 个）                                 | **建表时不内联**，全部延后 `ALTER TABLE`（PG 要求被引用表先存在）                         |
| `name TEXT COLLATE NOCASE` 唯一索引（tags）   | 列改 `citext` 扩展类型，保持大小写不敏感等值语义                                          |
| 3 个 `AFTER UPDATE/INSERT` 触发器             | 移植为 PL/pgSQL（`mc_banks_course_au` / `mc_banks_lesson_au` / `mc_questions_course_ai`） |

**没有**用到的特性（省了很多事）：`WITHOUT ROWID`、FTS5、JSON 函数、generated columns。

## 4. 工具链（已提交，可复用）

```bash
ops/scripts/pg/
├── gen-schema.mjs        # SQLite schema → PG DDL（含默认值/索引/外键/CHECK 转换）
├── post-schema.pg.sql    # citext + 3 个 PL/pgSQL 触发器（gen 之后执行）
├── export-tsv.mjs        # SQLite → 每表一个 TSV（COPY TEXT 转义，分页扫描）
├── load-pg.sh            # 建库 → 建表 → 补特性 → \copy 装载 → 重置序列 → 行数校验
└── verify-parity.sh      # 聚合指纹对比 + 关键查询耗时对比
```

```bash
# 标准用法（在 NAS 上，PG 容器可 psql）
node ops/scripts/pg/gen-schema.mjs  /path/microclass.db /tmp/schema.pg.sql
node ops/scripts/pg/export-tsv.mjs  /path/microclass.db /tmp/pg-export
bash ops/scripts/pg/load-pg.sh      mc-pg microclass /tmp/schema.pg.sql ops/scripts/pg/post-schema.pg.sql /tmp/pg-export
bash ops/scripts/pg/verify-parity.sh /path/microclass.db
```

要点：

- 装载用 `session_replication_role = replica` 关掉外键/触发器，装完再开（同一快照，顺序无关）。
- 装完必须 `setval(pg_get_serial_sequence(...), max(id))`，否则后续 INSERT 撞主键。
- 校验不能只看 `count(*)`：**行数 + `SUM(id)` + `SUM(LENGTH(文本列))`** 三项同时相等才可信。

## 7. 未完成 / 下一步（P0 的代码侧）

数据层"库"换好了，但**应用还在用 SQLite**。剩余工作：

1. **仓储层 async 化**：`apps/api/src/db/repositories/*` 全部改 `async`，`Db` 抽象换成 `pg.Pool`；
   `node:sqlite` 的同步调用点约 60+ 处，逐个改并补事务封装（`withTransaction`）。
2. **迁移脚本停止使用**：`schema_migrations` 由 PG 侧迁移工具管理（或保留同一张表，改为执行 PG 方言 SQL）。
3. **`unixepoch()` 语义**：现库大量 `INTEGER` 时间戳（epoch 秒），PG 端保持 `bigint` 以免全量改代码；
   后续可平滑升级到 `timestamptz`。
4. **citext 扩展**：目标库需允许 `CREATE EXTENSION citext`（本次已验证可用）。
5. **连接池参数**：`max`、`idleTimeoutMillis`、`statement_timeout`、`application_name` 需按实例数规划
   （P1 多副本时每个副本池上限要乘副本数）。
6. **P1 起**：API 无状态化（会话→Redis）→ 多副本 + 反代 → 队列化体检/导入/转码。

```bash
sudo install -m 755 ops/deploy/backup.sh    /vol1/1000/microclass-deploy/backup.sh
sudo /vol1/1000/microclass-deploy/backup.sh      # 先手动跑一次确认

#   30 3 * * * /vol1/1000/microclass-deploy/backup.sh >> /var/log/microclass-backup.log 2>&1
```

## 9. 已发现的方言差异（迁移踩坑清单）

| #   | SQLite                               | PostgreSQL                                         | 处理方式                                                                                                                    |
| --- | ------------------------------------ | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 1   | `?` 占位符                           | `$1..$n`                                           | `toPgPlaceholders()` 统一重写（跳过单引号字符串）                                                                           |
| 2   | `INTEGER PRIMARY KEY AUTOINCREMENT`  | `bigint GENERATED BY DEFAULT AS IDENTITY`          | 生成器转换；序列装载后用 `setval(max(id))` 对齐                                                                             |
| 3   | `INSERT` 后取 `lastInsertRowid`      | 无此概念                                           | 统一改 `INSERT ... RETURNING id`（SQLite 3.35+ 也支持），两库同一句 SQL                                                     |
| 4   | `DEFAULT (datetime('now'))` 产出文本 | `now()` 是 timestamptz，赋给 text 列会**建表失败** | 生成器改为 `to_char(now() AT TIME ZONE 'utc','YYYY-MM-DD HH24:MI:SS')`；**已修**                                            |
| 5   | `DEFAULT (unixepoch())`              | 无内置                                             | → `(EXTRACT(EPOCH FROM now()))::bigint`（保持整数时间戳语义）                                                               |
| 6   | `name TEXT COLLATE NOCASE` 唯一索引  | 无 NOCASE 排序规则                                 | 列改 `citext`（保持大小写不敏感等值比较），索引随之重建                                                                     |
| 7   | 布尔存 `0/1` 整数                    | 可 `boolean`                                       | **暂不改成 boolean**：保持 `bigint`，服务层继续 `=== 1` 判断，避免全量改代码                                                |
| 8   | `LIKE` 默认对 ASCII 大小写不敏感     | `LIKE` 大小写敏感                                  | 搜索类查询若依赖不区分大小写，需 `ILIKE` 或 `lower()`（**待排查**：题库/课程搜索）                                          |
| 9   | 外键可引用后建的表                   | 被引用表必须先存在                                 | 生成器把 21 个外键延后为 `ALTER TABLE`                                                                                      |
| 10  | 无 `RETURNING` 的行数统计            | `rowCount`                                         | `AsyncDb.run` 统一返回 `{ changes }`                                                                                        |
| 11  | 事务 `BEGIN IMMEDIATE`               | `BEGIN` + 连接池独占                               | `AsyncDb.transaction()` 在 PG 用单连接（`pool.connect`），SQLite 沿用 `BEGIN IMMEDIATE`                                     |
| 12  | 触发器语法 `BEGIN ... END`           | `LANGUAGE plpgsql` + `RETURN NULL`                 | 3 个触发器手工移植（见 `post-schema.pg.sql`）                                                                               |
| 13  | `db.transaction(() => …)` 同步回调   | 无对应（必须 async）                               | 批量写统一改 `db.transaction(async (tx) => …)`，**回调里的语句用 `tx`**（B3b 已改 `setBankSections` / `setCourseBindings`） |
| 14  | `lastInsertRowid`                    | 无                                                 | 题库 `create` 改用 `INSERT … RETURNING id`（同时去掉 `lastInsertRowid` 依赖）                                               |

> **事务语义已验收**：`apps/api/test/bank-write-transaction.test.ts` 断言「一条失败 → 整批回滚」
> （sqlite 实跑 8 条；PG 分支写在同一个文件里，用 `MC_PG_TEST_URL` 触发，按硬规则不在生产机跑）。
>
> **过渡函数已清零**：`BankRepository.findByIdSync` 已删除，`prepareQuestionInput` 改为 async，
> PG 模式下不会再出现「写走 PG、校验读 SQLite」的隐患。

> **仍未验证的方言点**（迁移到对应域时要重点测）：`LIKE`/`GLOB` 大小写、`json_extract`（本库未用）、
> 聚合里的字符串拼接 `||`（两库一致）、`GROUP BY` 下的 `count(distinct)` 行为、`LIMIT ? OFFSET ?` 参数绑定。

```bash
PASS=$(grep '^MC_PG_PASSWORD=' /vol1/1000/microclass-deploy/.env | cut -d= -f2-)
MC_PG_TEST_URL="postgres://microclass:${PASS}@db:5432/microclass_test" \
  bash /vol1/1000/mc-pg-test/ops/scripts/pg/run-pg-tests.sh
```

实测输出（2026-11-26）：

```
✓ apps/api/test/pg-announcements.test.ts (4 tests) 557ms
```

## 12. 预发/压测的生产保护（必读）

2026-11-26 两次生产卡顿都是同一类：**同步 `node:sqlite` + `/vol1` 机械盘被压满**，事件循环被一次读盘卡住，
全站无响应几十秒到几分钟（看门狗能恢复，但会中断服务）。

**硬性约定**：

1. **预发实例的数据副本放 NVMe**（`/var/lib/mc-preprod-data`），不要放 `/vol1`；
   预发启动时读 1.2 GB sqlite 副本足以把机械盘打到 99% util。
2. **重活只在 01:00–06:00 跑**：PG 重装（`load-pg.sh`）、`pg_dump` 全库备份、全表聚合体检、大批量导入。
3. **预发前先过 IO 门槛**（util > 70% 直接退出）：

   ```bash
   $ sudo bash ops/scripts/pg/guard-io.sh           # 超 70% 退出 1
   $ MC_IO_MAX=60 sudo -E bash ops/scripts/pg/guard-io.sh
   $ MC_IO_WAIT=1 sudo -E bash ops/scripts/pg/guard-io.sh   # 等待（最多 10 分钟）
   ```

   实测样例：

   ```
   [2026-11-26 03:12:44] /vol1 util=8%（阈值 70%）
   ✓ 磁盘压力可接受，继续
   ```

   失败样例（事故当时）：

   ```
   [2026-11-26 02:57:30] /vol1 util=100%（阈值 70%）
   ✗ /vol1 当前 util=100%（> 70%），为避免拖慢生产，本次预发取消
   ```

4. 预发脚本模板（`build/pg-migration/preprod-*.sh`，不入库）：起容器前先跑 `guard-io.sh`，
   数据目录用 NVMe 副本，结束后 `docker rm -f` 立即清理。

### 12.1 「本机不再跑预发」检查清单（跑之前逐条确认）

> 2026-11-26 三次生产卡顿（02:57、03:48、04:38）**全部**发生在「同机起预发容器 / 并行对比」时。
> 结论：**只要生产还在用同步 SQLite，就不要在同一台 NAS 上起预发实例**。

```bash
# 1) 是否还有预发容器在跑？（应为空）
sudo docker ps -a --filter name=mc- --filter name=preprod --format '{{.Names}} {{.Status}}'

# 2) 8097 等预发端口是否被占用？（应无输出）
sudo ss -ltnp | grep -E ':(8096|8097|8098)\b'

# 3) 有没有并发的镜像构建 / npm / apt 在吃盘？（应无 build-image.sh）
pgrep -af 'build-image.sh|npm|docker build' | head

# 4) 磁盘压力是否可接受？（≤70% 才动手）
sudo bash ops/scripts/pg/guard-io.sh

# 5) 生产此刻是否健康？（必须 200）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8091/api/v1/healthz
```

**做任何预发前，必须同时满足**：1 和 2 为空、3 无构建、4 通过、5 为 200。
否则先等（或用 `MC_IO_WAIT=1 guard-io.sh` 等盘），**不要“顺手跑一下”**。

### 12.2 切流预演草案（需要用户确认窗口后才执行）

**前置条件**

- `main` 上所有域已迁移完、`MC_DB=sqlite` 全绿（vitest / E2E 40 / eslint / build / size）
- PG 侧数据与 SQLite 一致：`verify-parity.sh` 10 组指纹一致；`schema_migrations` 已对齐
- 备份就绪：`pg_dump -Fc` 一份 + SQLite 卷 tar 一份，都在 `/vol1/1000/microclass-backup/`
- 回滚路径演练过：`echo 2.3.2-stable > .image-tag && bash redeploy.sh` 能在 1 分钟内恢复

**窗口**：建议 01:00–06:00，预留 **60 分钟**（实测纯切换约 5 分钟，其余留给验证与回滚）

**执行顺序**

```bash
# 1) 停 API（避免切流期间的写入落到 SQLite）
sudo docker compose -f /vol1/1000/microclass-deploy/compose.evo4.yml stop api
# 2) 备份 SQLite（停写后的一份干净副本）
sudo bash /vol1/1000/microclass-deploy/backup.sh
# 3) 切库：.env 里 MC_DB=pg + MC_PG_URL=postgres://microclass:***@db:5432/microclass
sudo sed -i 's/^MC_DB=.*/MC_DB=pg/' /vol1/1000/microclass-deploy/.env
# 4) 起 API（新镜像需已构建：microclass:<版本>）
sudo bash /vol1/1000/microclass-deploy/redeploy.sh
```

**回滚（任一验证失败立即执行）**

```bash
sudo sed -i 's/^MC_DB=.*/MC_DB=sqlite/' /vol1/1000/microclass-deploy/.env
```
