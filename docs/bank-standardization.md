# 题库标准化与多样化建设

微课堂的题库来自本地教辅题库（`题库_教师版`：33.98 万题 / 44.19 万图，按
`学科/书册/章节/知识点/题目.md + images/` 组织）。要把这么大的库真正用起来，
需要两件事：**标准化**（同一套字段、同一套写法，能筛、能查重、能统计）和
**多样化**（同一知识点有多来源题目、有整卷、有难度分层，组卷和练习都有得挑）。

## 1. 标准化

### 1.1 字段（迁移 `0008_question_metadata.sql`）

| 表          | 字段                         | 说明                                                           |
| ----------- | ---------------------------- | -------------------------------------------------------------- |
| `questions` | `subject` / `stage`          | 学科（数学/物理/化学）、学段（小学/初中/高中）                 |
| `questions` | `book` / `chapter` / `point` | 书册 / 章节 / 知识点（可直接按知识点筛题、组卷）               |
| `questions` | `source_path`                | 题库里的目录（`数学/七年级上册/…/有理数乘方`），可回溯到原文件 |
| `questions` | `source_no`                  | 原平台题号（对账、查重时用）                                   |
| `questions` | `content_hash`               | **内容指纹**：题干归一化 + 选项归一化后的 sha1                 |
| `banks`     | `kind`                       | `lesson` 课时配套 / `chapter` 章节题库 / `paper` 整卷试卷      |
| `banks`     | `subject` / `book`           | 题库的学科与书册（列表筛选用）                                 |

`content_hash` 只含「题干 + 选项」、**不含答案**，于是同一道题在不同册次/版本里重复出现能被认出来，
而「同题不同答案」也能被体检出来（多半是数据质量问题）。

### 1.2 题面与答案的写法归一化

打包阶段（`build/build-bank-manifest.mjs`）统一处理过这些事情，实测原数据里确实存在：

| 问题                                     | 处理                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------- |
| `##` / `###` / `__________` 三种空位记号 | 统一成 `____`（行首 `## 标题` 不误改）                                            |
| JSON 转义残留 `\\frac` / 字面量 `\n`     | `\\frac` → `\frac`；字面量 `\n` → 真换行（`\neq` 等命令不受影响）                 |
| 填空题答案写法乱                         | 空与空之间统一 `；`；同一空的等价写法用 `                                         | `（原数据 `@@`）；去掉 `$` 包裹 |
| 难度值（正确率）                         | ≥0.7 → `easy`、≥0.4 → `medium`、其余 `hard`                                       |
| 图片                                     | 内容寻址落盘（`uploads/question-media/<sha1 前两位>/<sha1>.<ext>`），题面内联引用 |

### 1.3 题库体检（API + 管理端）

`GET /api/v1/banks/health[?bankId=&limit=]`（教师/管理员）返回：

- **质量统计**：题目总量、未标难度、答案为空、带/不带配图、**重复题分组**、重复题数量、
  **同题不同答案（冲突）分组**、无指纹题数；
- **元数据覆盖率**：学科 / 书册 / 知识点 / 内容指纹各覆盖多少题、占比多少；
- **题库类型分布**：课时配套 / 章节题库 / 整卷试卷 各有几个题库、多少题；
- **重复题明细**：按出现次数排序的 Top N（题干 + 出现次数 + 答案种类）。

管理端「题库管理」页右上角 **题库体检** 按钮即可查看；题库列表新增 **按类型筛选**（课时配套 / 章节题库 / 整卷试卷）。

### 1.4 导入流程（可重复、可回填）

- 导入器 `ops/scripts/import-bank-manifest.mjs`（随镜像发布）：
  - 课时配套题库按 `lesson_id` 幂等；章节题库 / 整卷试卷按**题库名**幂等（它们没有课时归属）；
  - 已有题库默认跳过，但会**自动回填标准化元数据**（`--no-backfill` 可关）；
  - 走只读挂载 `/import` 时结果写到 `<数据目录>/bank-import-results/`（包目录只读也不会白跑）；
  - 命中 SQLite 锁错误（NAS 慢盘并发写会偶发 `database is locked`）按 1s/2s/3s… **退避重试**；
- 批量脚本：`build/evo4-import-mounted.sh`（宿主解包 + 容器内导入，按包名记账，中断可重跑）、
  `build/evo4-import-loop.sh`（反复跑到没有新包为止）；
- 预计算列 `questions.has_image`（迁移 `0009`）：导入时写入，老数据用
  `ops/scripts/backfill-has-image.mjs` 回填一次（36.6 万题约 2 分钟），体检不再 LIKE 全表扫描。

### 1.5 去重（题库内）

`POST /api/v1/banks/:id/dedupe`（教师/管理员，**默认 dry-run 只预览**）：

- 判定：同一题库内「题干 + 选项」指纹相同**且答案一致** → 只保留最早的一条；
- **同题干不同答案的组不自动删**（属于数据质量问题，体检里「同题不同答案」单独列出）；
- 管理端题库面板 **清理重复题** 按钮：先弹预览（组数、可合并数量、样例），确认后才真删；
- 实测（全量导入后）：**全库可安全合并 2,443 组 / 2,505 道**；跨题库重复（同一道题同时出现在
  章节题库 / 整卷试卷 / 课时题库里）**按设计保留** —— 每个题库都要能独立组卷与练习；
  同题不同答案 771 组，需要人工核对。

### 1.6 「同题不同答案」核对

自动去重只解决「答案也一样的重复题」。**答案不一致**的组（题干 + 选项指纹相同、答案不同）不能自动处理：
删了会丢题，按多数自动改在票数相同时是瞎猜。做法是把它们变成一份**可逐组核对的台账**：

- **物化台账**（迁移 `0010`）：全库扫描按 `content_hash` 分组、`COUNT(DISTINCT answer) > 1` 的组写进
  `question_conflicts`（状态、选定答案、题干样例、组内题量、答案种类数、复核人、时间）；
- **台账保鲜**（迁移 `0011`）：`question_conflict_meta` 记下上次扫描的**题目 id 水位 + 时间**，
  `staleness()` 判定 `never / empty / grew / ttl / fresh`；
- **三种结论**：
  - `resolved` 选定答案 → **整组统一**为该答案（指纹相同意味着题干与选项相同，答案本应一致），
    记录保留在台账里作为核对历史，不会被下次扫描冲掉；
  - `ignored` 确认「答案不同是合理的」→ 不再出现在待核对列表，**题目保持原样**；
  - 已核对过的组**又被改回冲突**时自动打回 `pending` 重新提示；
- **批量按多数答案**（`POST /question-conflicts/resolve-majority`）：默认只预演（返回组数/题数/样例），
  `dryRun=0` 才落库；**票数并列的组跳过不猜**，留给人工；
- **API**：`GET /question-conflicts`（分页、`status=pending|resolved|ignored|all`、每组答案分布）、
  `GET /question-conflicts/:hash`（组内每题的题库、类型、难度、来源单号）、
  `POST /question-conflicts/:hash/resolve|ignore|reopen`、`POST /question-conflicts/sync`；
  全部写操作要求教师/管理员，核对动作写审计日志（`question_conflict.resolve` / `.ignore`）；
- **管理端**：`/admin/question-conflicts`（侧边栏「冲突题核对」）四个页签 + 逐组核对弹窗 +
  批量多数处理；题库体检的「同题不同答案」有「去核对 →」直达。

#### 台账扫描：为什么必须由用户点按钮触发（真机教训）

- 扫描是**全库分组**（36.6 万题）。这台 NAS 的顺序写 26MB/s、**顺序读只有 ~1.9MB/s**
  （`VACUUM` 600MB 实测 386 秒）；
- `node:sqlite` 是**同步** API：扫描期间整个事件循环被占住，健康检查请求全部排队（日志里能看到
  扫描结束后一秒内涌入十几个 healthz）—— 如果放在列表接口里隐式触发，**打开页面就能把整站卡死**；
- 因此：`GET /question-conflicts` **从不扫库**，只报告台账状态（`stale` / `reason` / `ageMs`）；
  界面在过期时显示横幅提示，扫描只由「重新扫描全库」按钮或运维脚本触发；
- 扫描成本也压过（真机实测，同一台 NAS）：
  - 迁移 `0012` 加**覆盖索引** `(content_hash, answer)`：`EXPLAIN QUERY PLAN` 显示
    `SCAN questions USING COVERING INDEX idx_questions_hash_answer`，分组、`MIN/MAX(answer)`、
    `COUNT(DISTINCT answer)` 全部走索引，不再逐题回表读大字段题干（题干样例改为只对冲突的几百组单独取一次）；
  - 迁移 `0013` 删掉被它取代的 `idx_questions_content_hash`（前缀可用 → 纯冗余，只会增加写放大）；
  - `HAVING COUNT(DISTINCT answer) > 1` 换成等价的 `MIN(answer) <> MAX(answer)`，省掉每组的临时去重表；
  - 效果：**清空文件缓存后（最坏情况）整次扫描 1.1 秒**（扫描本身 129ms），热缓存 0.3 秒；
    优化前是「冷缓存 50 秒 / 容器刚重启后第一次 615 秒」；
  - 接口返回**分段耗时**（`ms.scan / cleanup / write / meta / total`），慢在哪一步一目了然。

#### 顺带修掉的一个指纹缺陷（原来的「771 组」大半是假阳性）

早期指纹把图片标记**整段删掉**（`![](url)` → 空），理由是「同一题在不同包里的图片地址可能不同」。
但题库图片是**内容寻址**的（`/api/v1/question-media/<sha1>.<ext>`），同一张图地址必然相同 ——
这条理由不成立，反而把「计算 ![图A]」和「计算 ![图B]」**两道不同的题**并成一组。
真机实测（修正前）：771 组里 **555 组**题干带图片，最大的「一组」有 **280 道题、41 种答案**
（其实是一批不同的看图计算题）。

修法：指纹改为**只保留图片地址**（`![alt](url)` → `url`）。修正后真机结果：

| 指标               | 修正前 | 修正后                                                               |
| ------------------ | ------ | -------------------------------------------------------------------- |
| 冲突组             | 771 组 | **207 组**（627 组假阳性被拆掉，另有 62 组真冲突被认出来）           |
| 涉及题目           | 上万道 | **1,201 道**                                                         |
| 最大组             | 280 题 | **18 题**                                                            |
| 单组最多答案种数   | 41 种  | **2 种**（少数 3–5 种）                                              |
| 重复题分组（体检） | 71,281 | 78,920（把「题干同、图不同」的假重复拆开，拆出的子组本身也是真重复） |

- 「同题不同答案」台账不再有这类假阳性，老师看到的是真的同一道题（示例：
  `计算：$-1^{2018}+|1-\sqrt{2}|-\sqrt[3]{8}=$` 的答案写成 `\sqrt{2}-4|-4+\sqrt{2}`（16 票）与
  `\sqrt{2}-4(或)-4+\sqrt{2}`（2 票）—— 这类「同义写法」占了相当一部分，点一下「按多数答案」即可统一）；
- 题库内去重也不会再把「题干相同、图不同」的题当重复题删掉（更安全，可能少合并一些真重复）；
- 老数据用 `ops/scripts/backfill-question-meta.mjs --only rehash` 全量重算指纹
  （幂等；真机 36.6 万条**实测 572 秒**，建议停服后独占执行，见 [ops-runbook.md](ops-runbook.md)），
  重算后要重新扫一次台账。

### 1.7 体检性能

库到 620MB / 36.6 万题、数据卷在 NAS 机械盘上时，**冷缓存的全表扫描是真瓶颈**
（顺序写 26MB/s，但顺序读只有 ~1.9MB/s，读一遍整库要五分钟级）：

- 体检从 10 条独立聚合（含三列 `LIKE` 全表扫描）改成 **2 条 SQL**（1 次全表聚合 + 1 次按指纹分组），
  结果**缓存 5 分钟**（`GET /banks/health?refresh=1` 强制重算）；
- 连接层加 `temp_store = MEMORY`、`cache_size = 64MB`、`mmap_size = 256MB`；
- **把剩下的全表扫描也消灭掉**（真机实测「全新进程 + 清空文件缓存」这一最坏情况）：
  - 迁移 `0012` 覆盖索引 `(content_hash, answer)`：重复题分组聚合走纯索引扫描；
  - 迁移 `0014` / `0015` **部分索引**（只存 `= ''` 的行，各几十行）：
    `difficulty / answer / content_hash / subject / book / point` 的空值统计变成走小索引，
    覆盖率统计改成 `总数 − 空值数`（原写法 `col <> ''` 无索引可用）；
  - `duplicateGroups` 不再用 `MIN(stem)` 参与分组聚合（那会回表读全部题干），
    改成先用覆盖索引算分组、只对要展示的 10 组各取一条题干；
  - 结果：**体检冷启动 36.6 秒 → 热缓存 0.24 秒**（优化前冷缓存实测 **11–14 分钟**，
    体检页看起来就是卡死）；冲突题重扫 **冷 0.3 秒 / 热 0.19 秒**；
  - `build/verify-health-plan.mjs` 用 `EXPLAIN QUERY PLAN` 把这些查询钉住：任何一条退回全表扫描都会失败。

### 1.8 题库页首屏：去掉 `/lessons` 全量与「每个题库一次 COUNT」

- 前端在拉课时下拉时调了 `GET /lessons` **全量**（36.7 万题的真机上实测 **102 秒**），
  而该下拉在树形筛选改造后已废弃 → 直接删掉这次调用，课时改从 `/banks/catalog` 取；
- `GET /banks` 原写法对**每个题库**做一次 `COUNT(*)` 子查询 → 迁移 `0019` 新增
  `banks.question_count`，由题目增删改（`create/update/delete/deleteMany`）**同步维护**
  - 一次性回填（真机「题量与题目数不一致」= 0），另给 `POST /banks/fix-question-counts` 兜底修数；
- 列表改为分页（`limit` 默认 300 / 上限 500、`offset`，返回 `{ banks, total }`）；
- 真机实测：`GET /banks?limit=300` **热缓存 3–5 ms**、冷缓存 1.9–14 s（修复前 100 秒级）；
  `GET /banks/catalog` 热 11 ms、`GET /banks/catalog?courseId=` 4.7 ms。

> **冷缓存的数字要按「首次触盘」理解，别当成 SQL 慢**：这台 NAS 上除微课堂还跑着一台
> 4GB 的 Windows 虚拟机（qemu）和厂商 NAS 代理，文件缓存经常被挤掉。
> 用 `vm.drop_caches` 清缓存后同一个接口连打两次：
> `banks/health` 第 1 次 **66 s** / 第 2 次 **1.6 ms**，`banks?limit=300` 第 1 次 **1.9 s** / 第 2 次 **4.9 ms**，
> 组卷页用到的 `GET /exams/:id/paper` 冷 **168 s** / 热 **0.17 s** ——
> 差别几乎全在磁盘首次触盘（顺序读 ~1.9 MB/s），不在查询写法。
> 所以：**判断「某页慢」先用热缓存复测一次**，否则会把慢盘误判成查询或前端缺陷。

### 1.9 答案里的裸 LaTeX 与「解析只有图片」

两类都是**采集原样**造成的显示/可用性问题，真机量化过：

| 现象                                               | 真机规模                                | 处理                                                                                                                          |
| -------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 答案是**不带 `$` 的裸 LaTeX**（`\frac{3}{9}        | \frac{1}{3}；4`）                       | 待核对 1,201 题里 458 题（38%）                                                                                               | 前端 `utils/answer.ts` + `AnswerText.vue`：识别裸 LaTeX 交给 KaTeX、` | ` 拆「或」、`；` 拆多空（**只影响展示**，判分与写库仍用原文） |
| 解析**除了图片一个字都没有**（图片是解析文字截图） | 全库 366,867 题里 **19,507 题（5.3%）** | 迁移 `0020` 预计算列 `analysis_media_only` + 部分索引；体检给数量、`?mediaOnlyAnalysis=1` 可筛；行内渲染不再把整幅图压到 56px |

- 裸 LaTeX 判定用**命令白名单**（`\frac`、`\sqrt`、`\pi`…）而不是「反斜杠 + 字母」：
  后者会把 `C:\Users\test` 这种文本误判成公式；
- `|` 只有当拆出来没有空片段时才算分隔符 —— `|1-\sqrt{2}|`（绝对值）保持原样；
- 「解析只有图片」的判定口径见 `apps/api/src/domain/question.ts` 的 `hasMediaOnlyAnalysis()`：
  有 markdown 图片（本站题图或 http(s) 外链）且去掉图片标记后一个字都不剩；
- **OCR 评估过但没有采用**：tesseract + chi_sim 在真机 5 张样本上，中文正文大致可读但错字不少
  （【分析】→【分计】；【详解】→【详钙】），**公式基本会坏**（`-0.0002024= -2.02x 10` 丢指数），
  单张 20–30 秒（NAS CPU）→ 1.95 万张代价极大而质量不足，因此保留图片为准确来源，
  平台只负责「能找出来 + 能编辑 + 能看清」。

## 2. 多样化

| 维度        | 做法                                                                                                                         | 现状                 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| 课时配套    | 每个匹配到知识点的课时一个题库，学生看完视频直接做配套练习                                                                   | 3,675 个 / 10.6 万题 |
| 章节题库    | 没匹配到课时的知识点变成「章节题库」（不挂课时），可浏览、可组卷                                                             | 7,088 个 / 20.0 万题 |
| 整卷试卷    | `综合题 / 期中 / 期末 / 单元测试` 变成「整卷试卷」题库，一份卷子一个题库                                                     | 1,513 个 / 6.1 万题  |
| 多来源聚合  | 同一知识点在不同册次/版本都有题；`GET /questions/search?point=` 按知识点跨库找题，并给出该知识点的题量、难度分布、来源题库数 | 已支持               |
| 难度分层    | 组卷支持**难度配额**（`difficultyQuota: {easy,medium,hard}`，可与题型配额同时用，题量不足返回 `shortfall`）                  | 已支持               |
| 整卷 → 考试 | 整卷试卷题库一键建考试（`POST /banks/:id/exam`）                                                                             | 已支持               |
| 题型        | 题库以单选 / 填空为主；导入器支持多选 / 判断 / 解答（`short` 不自动判分）                                                    | 见体检页题型分布     |

> 说明：原教辅题库只有单选与填空两种题型，所以「题型多样化」不是导入能解决的；
> 平台侧的做法是：整卷试卷直接形成考试、同一知识点多来源聚合扩大可选面、
> 难度分层让基础题与压轴题各归其位。
