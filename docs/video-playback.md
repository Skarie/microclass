# 视频播放：现状、问题与目标架构

> 目标：**点开 1 秒内起播**、拖动秒响应、手机端可用、900 人并发不崩。
> 本文基于本项目实测（NAS：Intel N150 / 16GB / 1GbE / 磁盘 1.3GB/s / 免费空间 115GB）。

## 一、现在为什么慢（已实测）

| 现象                     | 根因                                                                       | 状态                                  |
| ------------------------ | -------------------------------------------------------------------------- | ------------------------------------- |
| 点进课时要等很久才开始播 | mp4 的 `moov` 在文件尾部，浏览器必须下完整片才能播（150MB 的片子就是这样） | 已修：faststart（moov 前置）          |
| 重看还得再下一遍         | 视频响应是 `cache-control: no-store`                                       | 已修：`private, max-age=86400` + ETag |
| 部分媒体库还是慢         | 媒体目录是**只读挂载**，系统无法原地重封装                                 | 待定：改 `:rw` 或入库前处理           |
| 服务端本身不慢           | TTFB 2~6ms、1MB/5ms、20 路并发 623MB/s                                     | 不是瓶颈                              |

**但即使 faststart 全部做完，MP4+Range 这套仍有天花板**：

- 单一码率，弱网/手机端没有降档空间；
- 拖动/跳转要靠二次 Range 请求，网络差时"转圈"；
- 900 并发按 4.5 Mbps 算要 4 Gbps，远超 1GbE —— 必须降码率；
- Node 直接吐大文件会占用事件循环（重查询时视频会卡，之前实测掉到 0.86 MB/s）。

## 二、目标架构（推荐）

```
上传/挂载
  └─ 入库流水线（后台队列，不阻塞请求）
       ├─ ffprobe 探元数据 + 抽封面（已有）
       ├─ 重封装 faststart MP4（-c copy，几秒/片）
       ├─ 生成 HLS：fMP4 分片 + master playlist（-c copy，不重编码，约 1.1 倍存储）
       │     └─ 需要降码率时再按档转码：360p(0.5M) / 480p(1M) / 720p(2M)
       └─ 写回课时（video_kind=hls，存 master 路径）
播放
  └─ 前端播放器
       ├─ 优先 HLS（hls.js；iOS 原生）
       ├─ 起播档位：先最低档（首片 1~2 秒内开始播），稳定后自动升档
       ├─ MP4+Range 兜底（HLS 还没生成完/浏览器不支持）
       └─ 预取下一课时首片
静态层
  └─ nginx 负责媒体（mp4 / HLS 分片 / 封面）
       ├─ sendfile + aio，零拷贝，不占 Node 事件循环
       ├─ Node 只做鉴权：校验通过后 X-Accel-Redirect 交给 nginx
       ├─ playlists: no-cache；分片: immutable, max-age=1y
       └─ HTTP/2（多分片复用连接）
可选
  └─ 视频迁对象存储/CDN（900 人高清的唯一解；NAS 只留 API）
```

## 三、为什么选 HLS（而不是 DASH / 继续 MP4）

| 方案                | 起播               | 拖动       | 自适应    | 移动端                     | 实现成本              |
| ------------------- | ------------------ | ---------- | --------- | -------------------------- | --------------------- |
| MP4 + Range（现状） | 依赖 faststart     | 二次请求   | ❌ 单码率 | 好                         | 已实现                |
| **HLS（fMP4）**     | **1~2 秒（首片）** | **按分片** | ✅        | iOS 原生、安卓/桌面 hls.js | 中（ffmpeg 一条命令） |
| DASH                | 同 HLS             | 好         | ✅        | 需 dash.js，iOS 不支持原生 | 中高                  |

关键点：**HLS 可以用 `-c copy` 生成，不需要重编码**（源是 H.264/AAC 时）。所以"做 HLS"这件事很便宜 —— 4 秒分片、1.1 倍存储、每片几秒 CPU。需要真正降码率时才重编码（N150 上 1 小时 720p 约需 1~2 小时，建议后台夜间批量）。

## 四、分阶段实施

### P0 播放体验（1~2 天，不改硬件）

1. **播放器双通道**：HLS 就绪时用 hls.js，否则回落到现有 MP4；
2. **起播策略**：`preload="metadata"` + 首片优先 + 预取下一课时首片；
3. **HLS 生成挂到入库流水线**（现有 faststart 服务里扩展，`-c copy`）；
4. 验收：起播 **< 1s**（本机/局域网）、拖动 < 300ms、首片体积 < 1MB。

### P1 静态层分离（半天）

1. NAS 上装 nginx（或复用 fnOS 自带反代），媒体走 `sendfile`；
2. Node 侧改为 `X-Accel-Redirect`（鉴权仍在 Node，媒体由 nginx 吐）；
3. 缓存策略：playlist `no-cache`、分片 `immutable`；
4. 验收：播放时 Node CPU < 10%，重查询不再影响视频（之前会掉到 0.86 MB/s）。

### P2 多码率与容量（按需要）

1. 后台批量转 360p / 480p / 720p（夜间跑，`-c copy` 能做的先做）；
2. 播放器默认 480p、弱网降 360p；
3. 存储测算：53.8GB 源 × 1.1（HLS remux）≈ 59GB；加 360p 档约 +10GB —— **115GB 可用空间够**；
4. 验收：900 并发拉 360p，1GbE 网卡吞吐 < 700 Mbps，失败率 0。

### P3 上限突破（成本项）

- 900 人看 720p 以上：必须 CDN/对象存储（按流量付费），或 2.5G/10G 网络；
- 这条不做，前面的优化也挡不住物理带宽。

## 五、入库流水线的任务定义（供实现）

| 任务        | 命令要点                                                                                                                | 耗时（N150）             | 存储              |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------ | ----------------- |
| faststart   | `ffmpeg -i in -c copy -movflags +faststart out`                                                                         | 144MB ≈ 2.6s             | 基本不变          |
| HLS（copy） | `ffmpeg -i in -c copy -f hls -hls_time 4 -hls_playlist_type vod -hls_segment_type fmp4 -hls_flags independent_segments` | 约 1~2 倍 faststart 时间 | ×1.1              |
| 360p/480p   | `-vf scale=-2:360 -c:v libx264 -preset veryfast -b:v 500k -c:a aac -b:a 64k`                                            | 1 小时视频 ≈ 1~2 小时    | 每档约源片 10~20% |

## 六、验收指标（可量化）

| 指标                     | 目标                      |
| ------------------------ | ------------------------- |
| 首帧时间（局域网）       | < 1s                      |
| 拖动响应                 | < 300ms                   |
| 单课时首片体积           | < 1MB                     |
| 播放时服务端 CPU（单流） | < 3%（nginx sendfile）    |
| 900 并发（360p 档）      | 失败率 0，网卡 < 700 Mbps |
| 重查询期间播放           | 不受影响（不出现缓冲）    |

## 七、现状与下一步

已完成：faststart 自动巡检、视频缓存头、交卷/看课并发优化（900 并发交卷 2.34s、看课 p95 1.42s，0 失败）。

**卡点**：两个媒体库是只读挂载（`/media/java`、`/media/sikuruike` 均 `:ro`），入库流水线无法原地处理。

下一步建议顺序：

1. 改挂载为 `:rw`（或把新视频放站内上传目录）；
2. 实现 P0（播放器双通道 + HLS 入库）；
3. P1 nginx 媒体层；
4. 按容量需要做 P2 转码；P3 视商业目标决定。
